# i18n

Every string a visitor reads comes from `src/locales/*.json`. There are two locales, `en` and
`tr`, and they stay at parity.

**Turkish is written but not published.** `ENABLED_LOCALES` in `src/i18n/index.ts` is `['en']`,
so the language switch is hidden and every visitor gets English. The Turkish copy is kept in sync
anyway; it ships when a native speaker has gone over it line by line. A translation that reads
like a translation is worse than no translation, and that call belongs to the person whose
language it is, not to the model writing it.

## Hard rules
- **No hardcoded user-facing strings in a component.** Not in a template, not in a computed, not
  in a default prop. A literal in the markup fails review.
- `const { t } = useI18n()` in `<script setup>`; `{{ t('scope.key') }}` in the template.
- A string carrying markup or a link uses `<i18n-t keypath="…">` with named slots — never string
  concatenation and never `v-html`.
- Counts go through the interpolation, not the template: `t('notes.count', { count })`.
- Adding a key to `en.json` without adding it to `tr.json` is an incomplete change.

## Not translated
Technology names, addresses and identifiers stay in `src/content/site.ts`: `Vue 3 · Nuxt`,
`github.com/denizzeybek`, the email, company names. Translating them would be wrong, not helpful.

## Keys
- Grouped by surface: `home.*`, `notes.*`, `note.*`, `contact.*`, `nav.*`, `notFound.*`.
- Named for meaning, not position: `home.headline`, not `home.text1`.
- Content that belongs to a data row is keyed by that row's id: `experience.<id>.summary`.

## Blog posts
A post is one file per language, named `<slug>.<locale>.md`, and the two share the same `slug`,
`date`, `tags` and `draft` value — the slug is what pairs them. `useNotes` shows the reader's
language and falls back to English when a translation is missing, so a post never disappears from
the list; the post page says plainly that it is showing the untranslated version. Post bodies are
markdown, not locale-file keys.
